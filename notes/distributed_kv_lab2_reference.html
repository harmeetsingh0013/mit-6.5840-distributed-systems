1. Learning History and Progression

  1. Started with a local mutex. This established the difference between protecting local Go memory and coordinating distributed clients.
  2. Moved to KV-backed locking. The logical lock became shared state stored in the KV service.
  3. Discovered the race in Get → Put. Two clients can both observe FREE unless the Put is conditional.
  4. Learned versions. A version records which state a client observed and lets the server reject stale updates.
  5. Passed the reliable lock tests. This established the basic conditional state-transition protocol.
  6. Encountered unreliable RPC. Retries introduced the deeper problem: the client may not know whether a mutation happened.
  7. Understood ErrMaybe. This separated server truth from client knowledge.
  8. Extended the lock for uncertainty. A per-lock-holder ID makes an ambiguous acquisition distinguishable.
  9. Finished Lab 2. The important result was not only passing tests, but understanding the protocol behind them.

2. Core Distributed-Systems Mental Model

For every distributed-systems problem, ask:

  1. What state exists?
  2. Who owns it?
  3. Who can modify it?
  4. What happens concurrently?
  5. What if a machine crashes?
  6. What if a request is lost?
  7. What if a reply is lost?
  8. What if messages are delayed or reordered?
  9. What does each participant know?
  10. What guarantee does the client observe?
Key habit: Do not ask only “what happened?” Ask “what can this client know from the messages it received?” This became especially important with ErrMaybe.

3. Key/Value Server

The KV service stores shared state indexed by a key. Conceptually:

Client A ───── RPC ─────→ KV Server
Client B ───── RPC ─────→ KV Server

KV server state:

"foo" → (value, version)
"bar" → (value, version)

A Get reads state. A conditional Put attempts to change state only if the client's expected version still matches the server's current version.

Server-side mutex

A mutex around the server's map protects local memory from concurrent RPC handlers. It is a Go concurrency mechanism, not a distributed coordination protocol.

Important distinction: “The server is thread-safe” does not mean “the distributed system is coordinated.” The server mutex can serialize individual RPC handlers while a client's multi-RPC protocol remains racy.

5. Versions and Conditional Put

A version is best understood as a stale-state detector / state-change number. It is not the lock owner.

Get("foo") → value = "FREE", version = 7

Put("foo", "A123", expectedVersion = 7)

The server conceptually does:

if currentVersion != expectedVersion:
    return ErrVersion

change value
increment version
return OK

This is similar to compare-and-swap: “change the state only if it is still the state I observed.”

Version isVersion is not
A change number tied to the key's state.The owner identity.
A way to reject stale updates.FREE/HELD state itself.
Something obtained from the server.A permanent local truth after the state may have changed.

6. The Get → Decide → Put Race

The central reliable-lock race:

Initial:
foo → FREE, version 10

Client A                         Client B
   │                                │
   │ Get → FREE, v10               │
   │                                │ Get → FREE, v10
   │                                │
   │ Put(A123, expected=10)        │
   │ ───────────────→ OK           │
   │                                │
   │                                │ Put(B456, expected=10)
   │                                │ ─────────────→ ErrVersion

Only one client can transition version 10. The server's conditional update provides the atomic point at which the competition is resolved.

Important lesson: Individual RPCs can be serialized by the server while the protocol spanning multiple RPCs is still concurrent. Atomicity must exist at the operation that decides ownership.

7. Unreliable Network

In the unreliable exercise, requests and replies may be dropped, delayed, or reordered. The client retries an RPC when it does not receive a reply.

Client                         Network                         Server

Put ───────────────────────────X
                         request dropped

Put ─────────────────────────────────────────────────────→ executes
                                    ←──────────────X
                                      reply dropped

From the client's perspective, both situations can initially look like “no reply.”

Why Get is easy to retry

Get does not mutate state. Repeating it does not create a second state transition.

Why Put is different

Put mutates state. The original request may already have succeeded even though the client never saw the reply.

8. ErrMaybe: The Client Does Not Know

Suppose the client sends a Put with expected version 7 and its reply disappears.

Case A — original Put executed

Client → Put(v7) → Server executes → version 8
                       ↓
                    reply lost

Client retries Put(v7) → ErrVersion

Case B — original Put never executed

Client → Put(v7) → request lost

Another client changes the key

Client retries Put(v7) → ErrVersion

The same retry result is compatible with two different histories. Therefore the client cannot honestly return a definite success or definite failure.

ErrMaybe means: “I do not know whether my original Put took effect.” It represents uncertainty in the client's knowledge, not uncertainty in the server's state.
SituationWhat client can know
Initial Put returns ErrVersionThe conditional update did not succeed against the observed version.
Request/reply outcome is uncertainThe client may not know whether the operation happened.
Retry produces ErrVersion after an ambiguous first attemptStill ambiguous; the first request may already have succeeded.

9. Distributed Lock Built on KV

The lock is not a new server. It is a protocol implemented on top of the KV service.

Logical lock name: "foo"

KV:
foo → FREE
   or
foo → owner-ID

Independent lock names are independent pieces of state:

foo → A123
bar → FREE
baz → B456

Reliable-network algorithm

  1. Read the current lock state.
  2. If free, conditionally change it to the caller's held state.
  3. If another client changed it first, retry.
  4. If held by someone else, wait/retry.
  5. Release only when the current ownership is appropriate.

10. Lock Name vs Owner ID

This was one of the most important conceptual corrections during the discussion.

IdentifierMeaning
locknameThe logical shared resource, e.g. "foo".
owner/Lock IDThe particular Lock object / holder that claims the resource, e.g. "A123".
                 same distributed lock
KV key: "foo"
        │
        ├── Client A's Lock object → id A123
        │
        └── Client B's Lock object → id B456

MakeLock("foo") creates a local handle to the logical lock. It does not create a new distributed lock.

Why lockname cannot also be the owner ID

lockname = "foo"

A stores: "foo"
B stores: "foo"

A's acquisition reply is lost.
A reads "foo".

A cannot tell whether A or B owns the lock.

The holder identity must therefore be distinguishable from the logical resource name.

11. Acquire Under Unreliable Communication

The central protocol after an ambiguous Put is:

Acquire
  │
  ├─ Get current state
  │
  └─ if free → conditional Put(myID)
                    │
          ┌─────────┼─────────────┐
          │         │             │
          OK    ErrVersion     ErrMaybe
          │         │             │
       acquired   retry        Get again
                                      │
                              ┌───────┴───────┐
                              │               │
                          value=myID      value≠myID
                              │               │
                           acquired       retry/wait

If ErrMaybe occurs and a subsequent Get shows the caller's ID, the caller can conclude that its acquisition took effect. If another ID or FREE is observed, it did not acquire the lock and should continue the protocol.

Key insight: The owner ID does not make the network reliable. It makes an ambiguous outcome observable from later state.

12. Release and Ownership

A safe release should not mean “if the key is HELD, make it FREE.” It should be tied to the current owner.

foo → A123

A calls Release

Get(foo) → A123

conditional Put(foo, FREE, observedVersion)

foo → FREE

If the stored value is B456, A should not release it. Otherwise one client could destroy another client's ownership.

Subtlety about ambiguous Release

A lost Release reply can also leave the caller uncertain. The general rule remains: a missing reply does not prove that the mutation failed. Later reads can provide evidence about the current state.

14. Findings and Learning Breakthroughs

  1. Distributed coordination is not local synchronization. A Go mutex solves a local memory problem; it does not coordinate separate clients.
  2. Atomicity must cover the ownership decision. Serializing individual RPC handlers is insufficient when the decision spans Get and Put.
  3. Conditional Put is the decisive race-resolution mechanism. It turns a stale observation into a rejected update rather than allowing both clients to win.
  4. A version is a freshness check. It says “this update is based on the state I observed,” not “I own this resource.”
  5. Retries do not make mutations automatically safe. Retrying a read is straightforward; retrying a mutation may duplicate or obscure the outcome.
  6. ErrMaybe is about knowledge. The server has a definite history; the client may not know which history occurred.
  7. Ownership identity resolves uncertainty. If the current lock value contains the holder ID, a later Get can reveal whether the ambiguous acquisition belongs to this client.
  8. Lock name and holder identity are different dimensions. The name identifies the resource; the ID identifies the current claimant.
  9. The distributed lock is a protocol layered over KV. No new lock server is required for the lab.
  10. Failure reasoning is more important than the happy path. The difficult cases are lost replies, stale versions, races, crashes, and ambiguous outcomes.

15. Misconceptions That Were Corrected

Initial intuitionCorrection
“A local mutex should make the lock safe.”Only if all participants share the same mutex; distributed clients do not.
“The server mutex means the lock operations are atomic.”The mutex protects each server operation; it does not make a multi-RPC client protocol atomic.
“Eventual consistency explains the Go map race.”No. Eventual consistency concerns distributed replicas; the race detector issue was unsynchronized local memory access.
“ErrVersion always means my Put failed.”Not after an earlier request/reply outcome became ambiguous. The first request may already have succeeded.
“The API has no owner ID, so ownership cannot be represented.”The Lock object can generate and store a local identifier and encode it in the shared KV value.
“The lock ID could just be the lock name.”Then every claimant has the same value, so an ambiguous acquisition remains ambiguous.
“MakeLock creates a new distributed lock.”It creates a local handle for a logical lock identified by the shared name.

16. Open Questions for Future Review

These are intentionally left as study questions rather than immediately answered.

1. If a client crashes while holding the lock, what happens to the lock under the Lab 2 design?
2. Why does the lab accept the possibility of a permanently held lock, and what would a production system need to change?
3. Is the owner ID required to be mathematically globally unique, or merely sufficiently unlikely to collide under the lab's assumptions?
4. What happens if two Lock objects in the same process use the same logical lock name but have different IDs?
5. Can Release be made fully robust against an ambiguous reply without introducing additional state or operations?
6. What exactly would “exactly once” mean for Put, and why is it harder than simply retrying?
7. Which guarantees come from the KV server, and which guarantees come from the lock protocol?
8. How would the protocol change if the server itself were replicated rather than a single KV server?
9. What happens if the lock value changes after a Get but before a conditional Release?
10. What is the connection between the “conditional update” idea in Lab 2 and Raft's rejection of stale terms/log information?

17. Bridge from Lab 2 to Raft

Lab 2 is an excellent foundation for Raft because it teaches the difference between state, knowledge of state, and safe state transitions.

Lab 2 conceptRaft connection
VersionRaft terms/log metadata help identify stale information and newer epochs.
Conditional PutRaft uses consistency checks and rules that reject stale log information.
ErrMaybeRaft also has delayed/lost RPCs where an old message may arrive after local state has changed.
Distributed lockRaft is a broader coordination/consensus protocol; its goal is agreement on an ordered log rather than ownership of one resource.
Shared KV stateA replicated state machine uses an agreed sequence of commands to drive replicated application state.
Important distinction: A distributed lock asks “who owns this resource?” Raft asks a much more general question: “what sequence of decisions should this group of servers agree has occurred?”
