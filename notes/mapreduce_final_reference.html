MapReduce — Final Reference & Learning Notes

A consolidated future reference for MIT 6.5840/6.824 MapReduce: concepts, implementation reasoning, debugging lessons, and distributed-systems insights learned during the lab.

Purpose: This is a reference, not a transcript. It emphasizes mental models, invariants, mistakes, and the reasoning that makes the implementation understandable.

1. Core Mental Model

MapReduce separates a large computation into two distributed stages:

Input files
    |
    v
+------------+
| MAP PHASE  |
+------------+
    |
    | intermediate key/value pairs
    | partitioned by key
    v
Intermediate files
    |
    | after ALL Map tasks finish
    v
+-------------+
| REDUCE PHASE|
+-------------+
    |
    v
Final output files

The application supplies mapf and reducef. The framework handles distribution, scheduling, partitioning, grouping, file organization, and recovery.

Core lesson: MapReduce is not primarily a word-count algorithm. It is a framework for distributing computation over large data while deterministically routing intermediate results to the correct Reduce task.

2. Architecture

ComponentResponsibility
Coordinator / MasterOwns task state, assigns work, controls Map → Reduce phases, handles WAIT/EXIT, and detects/reassigns stale work.
WorkerRequests work, executes Map or Reduce, performs file I/O, and reports completion.
Map functionApplication logic: input → []KeyValue.
Reduce functionApplication logic: (key, []values) → result.

The Worker does not decide whether it should do Map or Reduce. The Coordinator assigns a typed task.

Coordinator
    |
    +-- choose task
    +-- change task state
    +-- return task
    |
    v
Worker
    |
    +-- mapf/reducef
    +-- file I/O
    |
    +-- report completion
Important: The Coordinator is a scheduler/state manager, not the computation engine. Do not hold its mutex while executing Map or Reduce.

3. Map Phase

Map task X
  |
  +-- read input file
  +-- mapf(filename, contents)
  +-- []KeyValue
  +-- partition each key
  +-- write intermediate files
  +-- report completion

Example Map output:

("his","1")
("cat","1")
("his","1")
("dog","1")

4. Partitioning

The key routing rule is:

partition = ihash(key) % nReduce

Therefore every occurrence of the same key goes to the same Reduce partition, even when produced by different Map tasks.

"his" -> partition 3
"his" -> partition 3
"his" -> partition 3
Why? A Reduce task must see all values for a key in order to compute the final result for that key.

5. Intermediate Files

Use the mental model:

mr-X-Y
  | |
  | +-- Reduce partition Y
  +---- Map task X

If there are 8 Map tasks and 10 Reduce tasks, these are possible files:

mr-0-0 ... mr-0-9
mr-1-0 ... mr-1-9
...
mr-7-0 ... mr-7-9

They do not all need to exist.

What does Reduce Y read?

Reduce 0:
    mr-0-0
    mr-1-0
    ...
    mr-7-0

Reduce 1:
    mr-0-1
    mr-1-1
    ...
    mr-7-1

General rule: Reduce Y reads mr-X-Y for every Map task X.

Common confusion: mr-1-0 means Map task 1, Reduce partition 0. The first number is the Map number.

Empty partitions

A Map task may produce zero records for a particular partition. If your implementation creates files only for non-empty partitions, a missing file can legitimately mean an empty partition.

if errors.Is(err, os.ErrNotExist) {
    continue // valid empty partition
}
if err != nil {
    return err // real error
}

6. Reduce Phase

Reduce begins only after all Map tasks have completed.

all Map tasks Completed
          |
          v
    Reduce phase

Reduce task Y:

  1. Reads mr-X-Y for every Map task X.
  2. Collects records.
  3. Groups values by key.
  4. Calls reducef(key, values).
  5. Writes mr-out-Y.
  6. Reports completion.

Grouping is framework work

This was an important early confusion. The framework conceptually transforms:

("his","1")
("his","1")
("his","1")
("cat","1")

into:

"his" -> ["1","1","1"]
"cat" -> ["1"]

and then calls:

reducef("his", ["1","1","1"])
reducef("cat", ["1"])

The application Reduce function does not search across all files for occurrences of a key.

Final output

There is one final file per Reduce task:

mr-out-0
mr-out-1
...
mr-out-(nReduce-1)

It is not one file per word. Each file contains all results belonging to that Reduce partition.

             | Idle |
             +------+

Overall phase progression:

MAP PHASE
   |
   | every Map completed
   v

   |

A useful invariant is:

Map phase complete
    iff every Map task is Completed

Reduce phase complete
    iff every Reduce task is Completed

If you store both task states and separate completion booleans, keep them consistent. The task states are the authoritative conceptual state.

WAIT is important: there may be no currently Idle task even though existing tasks are still running.

10. RPC, Goroutines, and Mutexes

Go RPC handlers can run concurrently. Two Workers can request work at the same time.

Worker A -> sees Task 0 Idle
Worker B -> sees Task 0 Idle

A assigns Task 0
B assigns Task 0   <-- race/bug

The Coordinator needs a shared mutex around the check-and-update:

lock
    inspect task
    Idle -> InProgress
    prepare reply
unlock

Do the expensive Map/Reduce work outside the lock.

Distributed-systems lesson: Protect the shared state transition, not the expensive computation.

11. Worker Failure and Reassignment

If a Worker gets a task and crashes before reporting completion:

Worker A gets Map 3
       |
       v
Map 3 = InProgress
       |
   Worker A crashes
       |
       X no completion RPC

Without failure detection, Map 3 remains InProgress forever.

The Coordinator therefore needs a mechanism to eventually do:

InProgress -> Idle -> reassign

Health checks vs. task timeout

The original Google MapReduce paper discusses the Master periodically checking worker health. A lab implementation can instead track how long an individual task has been InProgress.

MechanismQuestion
Worker health checkIs this Worker alive?
Task timeoutHas this task been running too long without completion?

These are related but different mechanisms.

Scheduler interval is not timeout

scheduler interval = how often I inspect tasks
task timeout       = how long before I consider a task stale

For example, a scheduler could check every 200 ms while using a much larger failure threshold. Do not automatically make the check interval the timeout.

The exact timeout should be taken from the lab version/specification being used; do not rely on a remembered number from an older version.

TTL and Go struct copies

A subtle bug appeared when adding TTL metadata. This:

task.Task = c.MapTasks[index]

copies the struct. Updating:

task.Task.TTL = ...

updates the RPC reply copy, not the Coordinator's stored task. If the Coordinator later checks c.MapTasks[index].TTL, it will not see that update.

General Go lesson: When structs are assigned by value, always ask which copy is authoritative.

Late completion and duplicate execution

Failure detection is imperfect. A slow Worker can look dead:

t=0       Worker A starts Map 3
          |
timeout   Coordinator reassigns Map 3
          |
          v
          Worker B starts Map 3
          |
late      Worker A finishes

Now the same logical task may execute twice. This is normal territory for distributed systems: retries can create duplicate execution.

12. Test Lessons

TestMapParallel

Tests concurrency, not just final output. Holding the Coordinator mutex while executing Map would serialize work and defeat the intended behavior.

TestCrashWorker

Tests whether a task abandoned by a failed Worker can eventually be retried. An InProgress task that is never reclaimed can make the whole job hang.

TestJobCount

Tests execution behavior. It exposes unnecessary re-execution. If healthy tasks are incorrectly classified as stale, they can run more times than expected.

Important insight: Correct final output is not the only notion of correctness. A distributed system can produce correct output while still having incorrect task counts, races, poor concurrency, or failure-handling bugs.

13. Confusions and Their Final Answers

Question / confusionFinal mental model
Does Reduce group values?The framework groups values by key before calling the user Reduce function.
Does Reduce 0 read one file?No. It reads mr-X-0 from every Map X.
Do all intermediate files have to exist?No. Empty partitions can be represented by missing files in a sparse implementation.
One output file per word?No. One output file per Reduce task/partition.
Who gives the input filename?The Coordinator gives it in the assigned task.
Who chooses Map vs Reduce?The Coordinator, through the task type.
Why WAIT?No Idle task is currently available, but work is still running.
Can the Coordinator lock while Map runs?No; expensive work belongs outside the critical section.
Is 200 ms automatically the timeout?No; scheduler interval and failure threshold are different.
Why can TTL fail unexpectedly?Because the RPC task is a struct copy; Coordinator-owned state must be updated.
Why does a crash cause a hang?The task can remain InProgress forever unless stale work is reclaimed.
Why can JobCount fail after adding retries?Over-aggressive failure detection can re-run healthy/slow tasks.

15. What MapReduce Taught About Distributed Systems

  • RPC is unreliable communication: remote calls can fail or be delayed.
  • Failure is normal: workers can disappear without completing their work.
  • Concurrency creates races: multiple RPC handlers can touch the same state simultaneously.
  • State machines help reasoning: explicit task states make legal transitions visible.
  • Failure detection is imperfect: slow and dead are not immediately distinguishable.
  • Retries can duplicate work: re-execution must be tolerated.
  • Deterministic naming reduces coordination: both sides can derive mr-X-Y without exchanging every filename.
  • Correctness includes behavior: output, concurrency, task count, races, and recovery all matter.
  • Ownership matters: one component should have authoritative state.

16. The Most Useful Debugging Questions

When a MapReduce test fails, ask these in order:

  1. What state transition was supposed to happen?
  2. What state transition actually happened?
  3. Which component owns that state?
  4. Could two goroutines access it concurrently?
  5. Could a Worker have failed or simply been slow?
  6. Could the same task have executed twice?
  7. Is the failure about output, liveness, concurrency, or execution count?

18. Final Mental Model

MapReduce is a distributed execution framework.

The Coordinator turns a large computation into independently executable tasks. Workers execute those tasks concurrently. Map workers produce intermediate key/value data and deterministically partition it by key. After every Map task finishes, Reduce workers collect their partition from every Map task, group values by key, and produce one output file per Reduce partition. The Coordinator synchronizes task state, handles concurrent requests, and recovers from workers that disappear or become stale.

The deeper lesson is that the Map and Reduce functions are usually the easy part. The difficult part is coordinating concurrent machines when communication can fail, machines can disappear, and the same work may need to be performed more than once.
