1. Goroutines

Classification: A — Go/concurrency

go f() starts a function concurrently. It does not guarantee when it starts or finishes. Returning from main terminates the process even if other goroutines remain.

work()      // normal call
go work()   // concurrent execution

A goroutine is managed by the Go runtime; it is not literally an OS thread. A Java virtual-thread analogy is useful but not exact.

Rule: never depend on goroutine execution order unless synchronization establishes it.

2. sync.WaitGroup

Classification: A — Go/concurrency

A WaitGroup answers: “Have these goroutines finished?”

var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    // work
}()
wg.Wait()
  • Add(1): register work
  • Done(): report completed work
  • Wait(): block until the counter reaches zero

It does not start goroutines, protect shared state, make operations atomic, or communicate arbitrary values.

Important: Done() must mean the work is actually finished. Calling it at the start of a worker reports completion too early.

3. defer and LIFO

Classification: A — Go

defer schedules a call when the surrounding function returns. Multiple defers execute LIFO.

defer A()
defer B()
// return
B()
A()

For:

defer wg.Done()
mu.Lock()
defer mu.Unlock()

the return-time order is mu.Unlock(), then wg.Done().

4. Shared state

Classification: A — Go; C — MapReduce

Shared state is data multiple goroutines can access, such as counter, tasks, or task.status.

First question: Can multiple goroutines access this data concurrently?

5. Data races

Classification: A — Go/concurrency

A data race occurs when concurrent goroutines access the same memory, at least one access is a write, without appropriate synchronization.

counter++

Although one line, an increment conceptually involves read → add → write. Concurrent increments can interfere.

go run -race main.go

We used the race detector and saw Found 2 data race(s).

Rule: one source-code statement is not necessarily one atomic operation.

6. sync.Mutex

Classification: A — Go/concurrency

mu.Lock()
// critical section
mu.Unlock()

Idiomatic form:

mu.Lock()
defer mu.Unlock()
// critical section
ToolQuestion
WaitGroupAre these goroutines finished?
MutexWho may access this protected shared state right now?

7. Critical sections

Classification: A — Go; C — MapReduce

A critical section is the code that accesses/modifies protected shared state.

mu.Lock()
task := tasks[0]
tasks = tasks[1:]
mu.Unlock()

Rule: hold a lock only as long as necessary to maintain the shared-state invariant.

Do not keep a mutex locked across unrelated slow work such as a sleep, network operation, or long computation unless that operation genuinely requires the protected state.

8. Claiming shared work

Classification: C — Go concurrency + MapReduce

This is a check-then-act operation:

if task.status == "Idle" {
    task.status = "Running"
}

The check and update must be protected together:

mu.Lock()
if task.status == "Idle" {
    task.status = "Running"
}
mu.Unlock()

Otherwise two workers can both observe Idle and both believe they claimed the task.

Rule: protect the whole logical operation, not merely one line of it.

9. Slow work outside the lock

mu.Lock()
if task.status == "Idle" {
    task.status = "Running"
}
mu.Unlock()

doSomethingSlow(task)

After the shared state has been safely updated, the slow work can often proceed without the mutex. This lets another goroutine claim another task instead of waiting for the first worker’s slow operation.

Rule: protect shared state, not arbitrary work.

10. Values, pointers, slices, and shared data

Classification: A — Go

Go passes arguments by value, but a copied value can still refer to shared underlying data.

func change(s []int) {
    s[0] = 100
}

The slice header is copied, but the underlying array can still be shared. Therefore, synchronization decisions should be based on whether underlying data can be accessed concurrently—not merely on “pass by value.”

11. Concurrency reasoning workflow

Write concurrent code ↓ Identify shared state ↓ Identify the invariant ↓ Identify the critical section ↓ Protect it with synchronization ↓ Keep the critical section small ↓ Run with the race detector ↓ Interpret the result
  1. Which goroutines can run concurrently?
  2. What state do they share?
  3. Who reads and writes it?
  4. Can check-then-act be interrupted?
  5. What invariant must remain true?
  6. How much code actually needs the lock?

12. Connection to MapReduce

Classification: C — both

The MapReduce coordinator will maintain shared task state while multiple goroutines handle concurrent work.

Coordinator │ ├── shared task state │ └── task status │ └── concurrent goroutines │ └── Mutex protects state

A typical reasoning pattern is:

Lock
  inspect shared state
  make decision
  update shared state
Unlock
perform slow/non-shared work

We are deliberately postponing channels, select, RWMutex, atomics, and other advanced topics until the lab requires them.
